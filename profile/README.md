## 04 / THE ENGINEERING STANDARD

The same operating sequence applies across the collaboration:

```text
AUTHORITY  →  BOUNDED WORK  →  EXACT CANDIDATE  →  REVIEW
                                                     ↓
KNOWN STATE  ←  INTEGRATION  ←  TECHNICAL ACCEPTANCE  ←  CI / QA EVIDENCE
```

`Authority -> Bounded Work -> Exact Candidate -> Review -> CI/QA Evidence -> Technical Acceptance -> Integration -> Known State`

**Contributor route:** Find the owning work package → verify the source and scope → establish required START records → implement on an authorized branch → attach actual test/QA evidence → request review → record the final disposition and CLOSE records.

- **Common system first.** Department-specific workflow rules wait for validated LGU/process-owner decisions.
- **Contracts remain authoritative.** Frontend consumers do not invent backend permissions or lifecycle behavior.
- **Source and evidence matter.** A demo, issue label, or passing asset build does not establish production readiness.
- **Integration is a decision.** Kirch retains final technical integration and acceptance responsibility.

## 05 / FOLLOW THE LIVE STATE

The [Engineering Hub](https://github.com/Project-Intra-Smithy/engineering-hub) is the index, not a substitute for the repositories that own code and test results. Recheck the live branch, issue, and evidence before treating a dated status snapshot as current.
